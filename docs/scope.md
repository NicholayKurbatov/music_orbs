# Функциональные требования

Дата: 2026-10-17. Статус: проект спецификации для согласования.
Этап: реализация по [плану](implementation-plan.md); результаты и ограничения — в [tests.md](tests.md).

## 1. Цель и основной сценарий

Созерцательная интерактивная среда: выбрать объект → изменить его пальцем →
отпустить → наблюдать продолжающееся движение изменённой формы под музыку.
При отсутствии музыки сохраняется спокойная автономная анимация.

Форма — базовая процедурная геометрия. Материал — способ отображения частиц.
Деформация — постоянное изменение в локальных координатах объекта.
Анимация — временное движение поверх базы и деформации.
Медленный цикл — период по оценке BPM и числу тактов, не распознанная фраза.
Сессия — выбранная форма, настройки и деформации всех форм.

## 2. Функциональные требования MVP

| ID | Требование и критерий приёмки | Обязательность |
|---|---|---|
| FR-01 | Приложение устанавливается на Android 10+ и открывает сцену. Отсутствие аудиоразрешений не блокирует графику. | Основное |
| FR-02 | Выбор Orb, Ribbon, Cloud, Pixel Cloud; активна одна форма. При возврате к форме восстанавливается её собственная деформация. | Основное |
| FR-03 | Orb — объёмная сфера точек; Ribbon — перекрученная лента; Cloud — мягкое объёмное облако; Pixel Cloud — пространственная пиксельная структура. Все формы автономно вращаются, дышат или плавно изменяются. | Основное |
| FR-04 | Геометрия отделена от материала: точки, пиксели, мягкие частицы. В первом MVP достаточно четырёх настроенных пресетов. Неподдерживаемые сочетания не применяются молча. | Основное |
| FR-05 | Короткое касание вызывает локальное смещение, перетаскивание вытягивает или изгибает область. Сила влияния убывает с расстоянием; чувствительность регулируется. | Основное |
| FR-06 | После отпускания остаточное движение плавно затухает, постоянная деформация остаётся. Объект продолжает анимироваться относительно изменённой формы. | Основное |
| FR-07 | Деформация хранится в локальных координатах объекта и следует его вращению, а не фиксируется на экране. | Основное |
| FR-08 | Сессия сохраняется локально и восстанавливается после перезапуска. Повреждённые или несовместимые данные не блокируют открытие исходной сцены. | Основное |
| FR-09 | Reset возвращает активную форму к базовой геометрии и удаляет её сохранённую деформацию. Настройки и другие формы сохраняются. | Основное |
| FR-10 | Из полноэкранной сцены доступна панель: Shape, Material, Color/палитра, скорость и амплитуда Motion, Music Sync, Touch Sensitivity, Reset. Автоматическое движение включено по умолчанию. | Основное |
| FR-11 | Можно выбрать локальный аудиофайл, воспроизвести и приостановить его. Отмена выбора и неподдерживаемый файл дают понятный результат без потери формы. | Основное |
| FR-12 | Анализ текущего аудио формирует энергию, интенсивность, BPM с уверенностью и параметры медленного цикла. Графика не знает способ получения аудио. | Основное |
| FR-13 | В прежнем режиме основное движение использует 4, 8 или 16 тактов при допущении 4/4. Быстрые изменения дают малые акценты. Изменение оценки BPM не вызывает скачка фазы или скорости. | Основное |
| FR-14 | Тишина, отсутствие источника, низкая уверенность темпа и выключенный Music Sync сохраняют спокойное автономное движение. | Основное |
| FR-15 | Пользователь явно запрашивает захват внешнего воспроизведения. Захват начинается только после необходимых системных разрешений и согласия; отказ и отзыв объясняются. Совместимость зависит от источника. | Условное по устройству/источнику |
| FR-16 | Микрофон можно явно выбрать как резервный источник с отдельным разрешением и индикатором. Автоматической замены внешнего захвата микрофоном нет. | Резервный источник |
| FR-17 | При уходе в фон сцена приостанавливается, аудиоресурсы освобождаются. Возврат восстанавливает форму; аудио запускается по политике жизненного цикла. | Основное |
| FR-18 | Доступна настройка плотности частиц через детализацию и снижение частоты кадров. Изменение качества не теряет пользовательскую деформацию. | Основное |
| FR-19 | Ошибка и смена аудиоисточника не очищают форму; запоздалые данные старого источника не влияют на сцену. | Основное |
| FR-20 | Пресеты воспроизводят признаки REF-01–REF-04: зернистая округлая оболочка Orb с мягкими выпуклостями, складчатые полупрозрачные поверхности Ribbon, структурированные пиксельные слои Pixel Cloud. Точный туннель и буквальное копирование роликов не требуются. | Основное; уточнение FR-03 |
| FR-21 | Предусмотрены белая, розовая, лиловая и насыщенная многоцветная палитры по референсам. Палитра и её плавная смена не сбрасывают деформацию; поддержка цвета не ограничивается одним colorHex. | Основное; контракт расширяется до реализации |
| FR-22 | Пользователь явно выбирает внешний анализ через Visualizer: общий выходной микс либо доступную сессию плеера. Нужны обычные разрешения Android; root, ADB/DUMP, Shizuku и доступ к уведомлениям не обязательны. Текущий PCM capture остаётся отдельным способом. | 0.2.0; доступность условная по устройству/источнику |
| FR-23 | Частичные 8-битные окна Visualizer анализируются с реальными timestamps и независимо от непрерывного PCM. Энергия/акценты и BPM/confidence выдаются общему clock; разрывы, нормализация и низкая уверенность не создают ложного темпа или скачка фазы. | 0.2.0; точность проверяется fixtures и на устройстве |
| FR-24 | UI показывает выбранный способ и цель анализа, фактическое поступление данных, уровень, BPM или поиск темпа, выключенный Sync, отсутствие сессии/сигнала и недоступность эффекта. Режимы не подменяют друг друга скрытно; получение Android handle не означает совместимость с плеером. | 0.2.0 |
| FR-26 | В настройках доступна полная синхронизация: вращение и временные волны следуют подтверждённому BPM, замедляются при снижении темпа, ускоряются на атаках при том же BPM. Изменения плавные; Music Sync off/тишина возвращают автономное движение. Выбор сохраняется, прежний медленный режим доступен. | 0.2.1 |
| FR-25 | Новая устанавливаемая версия сохраняет applicationId, подпись обновления и сессии 0.1.0; версия APK увеличивается. Совместимость Honor 200 Pro/Яндекс Музыки подтверждается отдельной матрицей телефона и выхода, а не результатом эмулятора. | 0.2.0; проверка устройства отдельно от поставки APK |

Политики «собственная деформация каждой формы», «Reset только активной формы»
и остановка проигрывания в фоне — проектные уточнения исходной концепции,
предлагаемые для согласования перед реализацией.

## 3. Нефункциональные цели

| ID | Критерий | Подтверждение и открытые параметры |
|---|---|---|
| NFR-01 | Ориентир 60 FPS с резервным режимом 30 FPS. | Для выбранного эмулятора API 35 приняты medium/60, по 10 минут на пресет: p95 JS submission interval ≤20 мс, доля интервалов >25 мс <5%; p50 также записывается. Это частота отправки кадров, не подтверждение GPU/display FPS телефона. |
| NFR-02 | Непрерывность фазы и плавное изменение скорости. | Clock policy и допуски зафиксированы в spec.md; контрактные и G3-измерения, отдельная визуальная оценка. |
| NFR-03 | Атомарное локальное сохранение. | Ошибка записи не повреждает последний подтверждённый снимок; версии схем валидируются. |
| NFR-04 | PCM, окна Visualizer и FFT не отправляются в сеть и не сохраняются как аудиозапись. | Проверка потоков данных и хранилищ; анализ выполняется на устройстве; отчёты содержат только ограниченные скалярные измерения. |
| NFR-05 | Источники, DSP и графика заменяются независимо. | Домен не импортирует Android/Three.js; интеграция следует spec.md. |
| NFR-06 | Приемлемые память, нагрев и батарея. | Для выбранного эмулятора принят 30-минутный Orb: peak−initial PSS процесса приложения ≤32 МиБ. Отдельный WebView renderer/GPU может не входить в PSS; нагрев и батарея телефона остаются неизмеренными. |

Эти цели не являются уже подтверждёнными характеристиками приложения.

## 4. Границы MVP

Не входят: генерация форм ИИ, физика жидкостей, точное определение длинных
музыкальных фраз, аккаунты и облако, синхронизация устройств, библиотека
и плейлисты, системные живые обои, наложение поверх приложений, морфинг форм.
Visualizer(0) и Visualizer с сессией плеера реализованы в версии 0.2.0
по FR-22–FR-25; результаты исполнения перечислены в [tests.md](tests.md).
Обязательны адаптеры, честная диагностика и проверки; работа на каждом OEM/плеере
не гарантируется. В 0.2.0 не входят эквализация звука, root, патчинг плееров,
обход capture policy, скрытые API и обязательные DUMP/NotificationListener/Shizuku.
Нельзя обещать совместимость Spotify и Яндекс Музыки без проверки на устройстве.
Микрофон не заменяет захват музыки, звучащей в наушниках.

## 5. Принятые решения и открытые вопросы

- Реализованный стек: Kotlin, Compose, Three.js/WebGL в локальном WebView, Kotlin DSP.
- По умолчанию: размер 4/4, восемь тактов; 4/16 — политика музыкального движка.
- Один палец выполняет скульптуру; дополнительные указатели игнорируются. Управление камерой пока вне жестового сценария.
- В фоне проигрывание и захват останавливаются; автоматический повторный запуск микрофона не допускается.
- Сохраняется последнее успешно записанное состояние. Гарантия сохранения каждого движения при аварийном завершении не заявляется.
- Для текущей приёмки пользователь выбрал Android Emulator API 35 и бюджеты NFR-01/06. Физические устройства и сторонние плееры требуют отдельной матрицы.
- Пределы деформации, диапазоны настроек, BPM-допуски и сглаживание закреплены в [spec.md](spec.md). Их наличие не означает прохождение всех функциональных сценариев.
- Локальный pipeline декодирования/проигрывания проверен синтетической фикстурой G3; задержка относительно слышимого человеком звука ещё не измерена.
- Следующее расширение внешнего источника — Visualizer: сначала общий микс, затем доступные объявления сессий плееров. DUMP остаётся возможным отдельным будущим решением, не зависимостью 0.2.0.
- Внешний вид четырёх пресетов принят пользователем по нативным статическим кадрам G4; плавность и другие сочетания материалов оцениваются отдельно.

## 6. Готовность

Реализация начата по указанию пользователя после подготовки спецификации.
MVP принимается только после реализации основных требований, проверки условных
источников и проверки численных критериев на согласованной матрице. Результаты
текущего эмулятора не объявляются характеристиками физического телефона.

## Дополнение к статусу

Реализация начата после подготовки каркаса. Наличие исходника или интерфейса
не подтверждает его приёмку; завершение определяется проверенными сценариями.



## 7. Уточнение поведения форм

Это детализация FR-03–FR-06, а не четыре независимых системы анимации.

| Форма | Основное поведение | Прикосновение и вид |
|---|---|---|
| Particle Orb | Медленное вращение, мягкое дыхание округлой оболочки, выпуклости и перетяжки по REF-04 | Вытягивание, углубление, изменение симметрии; различимые мелкие точки и читаемый объём без пересвета |
| Particle Ribbon | Протяжённая складчатая поверхность по REF-01/03, волны, мягкое закручивание и изменение видимой ширины | Локальное вытягивание/изгиб; прозрачные перекрывающиеся слои и кромки как ткань; замкнутая лента Мёбиуса не обязательна |
| Particle Cloud | Очень медленное перераспределение и перетекание, изменения плотности при сохранении целостного силуэта | Сдвиг части облака, углубления и выступы; не случайный разлетающийся набор точек |
| Pixel Cloud | Структурированная слоистая композиция: квадратные элементы, решётки и вложенные рамки с глубиной по REF-02 | Общая локальная деформация; насыщенные многоцветные палитры с плавными переходами; случайной россыпи кубиков недостаточно |

Упругость/сопротивление может различаться по пресету, но механизм поля общий.
Несколько палитр и регулировка плотности реализованы; точные палитры и диапазоны
закреплены в [spec.md](spec.md). Сочетания вроде сферы из
пикселей и ленты из светящихся точек допускаются архитектурой, полная матрица
материалов не обязательна для первого MVP.
Pixel Tunnel с пролётом камеры — кандидат после MVP. Вложенные слои как
визуальный мотив уже относятся к Pixel Cloud, без добавления пятого ShapeId.
Cloud не имеет отдельного видеоэталона; внешний вид текущего пресета принят
по нативным кадрам G4. Морфинг с частичным сохранением деформаций — более поздняя возможность.
Визуальные основания: [references.md](references.md).

## 8. Последовательность и ориентиры развития

Это предварительные оценки из концепции при работе с кодовыми агентами
и регулярной интеграцией/проверкой человеком; они не являются обязательствами по срокам.

| Этап | Результат | Предварительный ориентир |
|---|---|---|
| Проверка реализуемости аудио | Индикатор уровня, разрешения, локальный файл, capture, микрофон, эксперимент Visualizer; матрица телефона/Spotify/Яндекс Музыки/динамика/Bluetooth | 1–2 рабочих дня |
| Графический прототип | Четыре формы, палитры, скорость/плотность, автономное движение, тестовые музыкальные сигналы и browser harness | 2–4 рабочих дня |
| Скульптура и сохранение | Общая деформация пальцем, затухание и локальное хранение | 2–4 рабочих дня |
| Музыкальный движок | FFT, энергия, оценка BPM/уверенности и плавные медленные циклы | 2–4 рабочих дня |
| Android-интеграция | Compose, WebView, настройки, локальное аудио и устанавливаемый APK | 2–4 рабочих дня |
| Приёмка и оптимизация | Жесты, lifecycle/разрешения, музыка, FPS, нагрев и батарея на устройстве | 2–4 рабочих дня |

Сначала снять риск доступа к аудио; при недоступности внешнего источника
продолжить с локальным файлом без попыток обхода ограничений.
Механику «движение → касание → сохранение → движение под музыку» сначала
проверять на Orb и Ribbon, затем расширить пресеты Cloud и Pixel Cloud.

Ориентиры по версиям: Visual Prototype — 3–5 рабочих дней; MVP Alpha с APK,
локальной музыкой и сохранением — 1–2 недели; MVP Beta с проверками внешних
источников и оптимизацией — 3–5 недель от старта. Эти вехи могут перекрываться
с этапами, их оценки не суммируются механически. Версия 1.0 — после тестирования
MVP и доработки эстетики/анализа/матрицы устройств. Сроки не обещают совместимость
с защищёнными внешними аудиоисточниками.
